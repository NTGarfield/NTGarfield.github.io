RTSP 笔记（二）：RTSP 协议基础与会话机制

1. 引言

RTSP（Real Time Streaming Protocol，实时流传输协议） 是一种面向实时媒体会话控制的应用层协议。

RTSP 的主要职责包括：

  • 获取媒体资源描述；
  • 协商媒体传输参数；
  • 建立媒体会话；
  • 控制媒体播放状态；
  • 管理会话生命周期。

RTSP 通常不直接承担音视频媒体数据本身的大规模传输。实际媒体数据通常由 RTP 等协议承载，RTSP 负责对这些媒体流进行控制。

本文重点介绍 RTSP 的协议结构和会话机制，包括：

  • RTSP Client 与 Server；
  • RTSP URI；
  • 请求与响应报文；
  • CSeq；
  • Session；
  • Transport；
  • 状态码；
  • 会话生命周期。

2. RTSP 协议定位

RTSP 属于应用层协议，其设计形式与 HTTP 存在一定相似性，采用文本形式的请求与响应消息。典型 RTSP 通信关系如下：

其中：

  • RTSP 用于媒体会话控制
  • RTP 用于媒体数据传输
  • RTCP 可用于媒体传输质量统计与同步
  • SDP 常用于描述媒体会话参数

RTSP 的核心对象并不是单个数据包，而是一个具有状态的媒体会话。

3. RTSP Client 与 RTSP Server

RTSP 通常采用客户端/服务器模型。

3.1 RTSP Client

RTSP Client 通常负责主动发起请求，例如：

  • 查询服务器支持的功能
  • 请求媒体描述
  • 请求建立传输通道
  • 启动播放
  • 暂停播放
  • 结束媒体会话

常见 RTSP Client 包括：

  • 媒体播放器
  • 视频监控客户端
  • 流媒体分析工具
  • 自定义音视频应用

3.2 RTSP Server

RTSP Server 通常监听指定网络端口，并处理客户端发送的 RTSP 请求。主要职责包括：

  • 解析 RTSP 请求；
  • 返回媒体资源信息；
  • 管理 Session；
  • 协商 RTP 传输参数；
  • 控制媒体发送状态；
  • 管理多个客户端连接。

RTSP 默认端口通常为 554 。实际系统中也可以配置其他端口。

4. RTSP URI

RTSP 使用 URI 标识媒体资源。典型形式：

rtsp://example.com:554/media/video

其结构可划分为：

字段 示例 说明
Scheme rtsp 协议类型
Host example.com RTSP Server 地址
Port 554 RTSP 服务端口
Path /media/video 媒体资源路径

例如：

rtsp://192.168.1.20/live/camera1

表示访问：

Server: 192.168.1.20
Resource: /live/camera1

URI 在后续 RTSP 请求中作为资源标识使用。

5. RTSP 报文结构

RTSP 使用文本形式的协议消息。其报文总体分为：

  • Request
  • Response

6. RTSP Request

典型请求：

DESCRIBE rtsp://example.com/media RTSP/1.0
CSeq: 2
Accept: application/sdp

RTSP Request 通常包含三部分：

Request-Line
Headers

Message Body

其中 Message Body 根据请求类型决定是否存在。

6.1 Request-Line

请求首行结构通常为：

METHOD URI RTSP-Version

例如：

DESCRIBE rtsp://example.com/media RTSP/1.0

字段含义：

字段 内容
Method DESCRIBE
URI rtsp://example.com/media
Version RTSP/1.0

Method 决定当前请求执行的操作。

7. RTSP Response

服务器收到请求后返回响应。典型响应：

RTSP/1.0 200 OK
CSeq: 2
Content-Type: application/sdp
Content-Length: 156

响应首行结构通常为 RTSP-Version Status-Code Reason-Phrase ，例如 RTSP/1.0 200 OK ，其中 200 表示请求处理成功。

8. RTSP 请求与响应对应关系

RTSP 通信采用请求—响应模型。例如：

Client:

DESCRIBE rtsp://example.com/media RTSP/1.0
CSeq: 2

服务器返回：

RTSP/1.0 200 OK
CSeq: 2
Content-Type: application/sdp

客户端通过 CSeq 判断响应对应的请求。

9. CSeq

CSeq 是 RTSP 中非常重要的头字段。典型形式：

CSeq: 1

下一条请求：

CSeq: 2

再下一条：

CSeq: 3

CSeq 可以理解为：

RTSP 请求的顺序编号。

服务器响应通常返回相同的 CSeq。例如：

Client                         Server
CSeq: 4  --------------------->
        <--------------------- CSeq: 4

因此客户端可以建立以下对应关系：

Request CSeq 4
      ↕
Response CSeq 4

10. 常见 RTSP 方法

RTSP 定义了多种请求方法。常见方法包括：

方法 主要作用
OPTIONS 查询服务器支持的方法
DESCRIBE 获取媒体资源描述
SETUP 建立媒体传输参数
PLAY 开始或继续播放
PAUSE 暂停播放
TEARDOWN 终止会话
GET_PARAMETER 获取参数或保持会话
SET_PARAMETER 修改参数

其中典型播放流程主要涉及：OPTIONS DESCRIBE SETUP PLAY TEARDOWN 。下一篇将进一步详细分析这些方法及其交互时序。

11. OPTIONS

OPTIONS 用于查询服务器支持的 RTSP 方法。请求：

OPTIONS rtsp://example.com/media RTSP/1.0
CSeq: 1

响应可能为：

RTSP/1.0 200 OK
CSeq: 1
Public: OPTIONS, DESCRIBE, SETUP, PLAY, PAUSE, TEARDOWN

其中 Public 用于表示服务器支持的方法集合。OPTIONS 通常用于能力探测，但并非所有 RTSP 会话都必须首先发送 OPTIONS 。

12. DESCRIBE

DESCRIBE 用于请求媒体资源的描述信息。典型请求：

DESCRIBE rtsp://example.com/media RTSP/1.0
CSeq: 2
Accept: application/sdp

服务器可能返回：

RTSP/1.0 200 OK
CSeq: 2
Content-Type: application/sdp
Content-Length: 200

v=0
...
m=video 0 RTP/AVP 96
a=rtpmap:96 H264/90000

消息体通常为 SDP。因此 DESCRIBE 的基本作用可以概括为：

SDP 中可能包含：

  • 音视频轨道
  • 编码格式
  • Payload Type
  • RTP 时钟频率
  • 控制 URI
  • 媒体参数

13. SETUP

SETUP 用于协商具体媒体流的传输参数。例如：

SETUP rtsp://example.com/media/track1 RTSP/1.0
CSeq: 3
Transport: RTP/AVP;unicast;client_port=5000-5001

其中最重要的字段为 Transport ，该字段用于协商：

  • RTP 传输协议
  • 单播或组播
  • UDP 或 TCP
  • 客户端端口
  • 服务器端口
  • interleaved channel
  • SSRC 等信息

14. Transport 头字段

Transport 是 RTSP 中最关键的头字段之一。典型 UDP 配置：

Transport: RTP/AVP;unicast;client_port=5000-5001

可以拆分为：

  • RTP/AVP 表示使用 RTP Audio/Video Profile。
  • unicast 表示采用单播。
  • client_port=5000-5001 通常表示客户端用于接收：
5000 → RTP
5001 → RTCP

服务器响应可能为：

Transport: RTP/AVP;unicast;
client_port=5000-5001;
server_port=6000-6001

表示：

Client RTP  : 5000
Client RTCP : 5001

Server RTP  : 6000
Server RTCP : 6001

15. Session

SETUP 成功后，服务器通常创建 RTSP Session。响应中可能包含：

Session: 12345678

该 Session ID 用于标识当前 RTSP 会话。后续请求需要携带：

Session: 12345678

例如：

PLAY rtsp://example.com/media RTSP/1.0
CSeq: 4
Session: 12345678

服务器可以据此判断 PLAY 操作属于哪个会话。

16. Session 与 TCP Connection 的区别

Session 与 TCP Connection 不是同一概念。TCP Connection 属于 传输层 ：

Client IP:Port
        ↕
Server IP:Port

RTSP Session 属于 应用层 ：

Session: 12345678

二者之间没有简单的一一对应关系。一个 TCP 连接可能承载一个或多个 RTSP 操作，而 RTSP Session 的生命周期也不应简单等同于某个 TCP socket 的生命周期。因此：这一点在后续分析连接断开、会话超时和重连机制时非常重要。

17. PLAY

PLAY 用于启动媒体发送。典型请求：

PLAY rtsp://example.com/media RTSP/1.0
CSeq: 4
Session: 12345678

服务器响应：

RTSP/1.0 200 OK
CSeq: 4
Session: 12345678

响应成功后，媒体服务器开始按照已经协商好的 Transport 参数发送媒体数据。

这两个阶段必须区分。SETUP 负责配置媒体通道，PLAY 负责改变媒体会话状态。

18. PAUSE

PAUSE 用于暂停当前媒体播放。例如：

PAUSE rtsp://example.com/media RTSP/1.0
CSeq: 5
Session: 12345678

暂停通常不会立即销毁 Session。因此后续仍可以发送 PLAY 恢复媒体传输。

19. TEARDOWN

TEARDOWN 用于终止 RTSP Session，并释放相关服务器资源。请求：

TEARDOWN rtsp://example.com/media RTSP/1.0
CSeq: 6
Session: 12345678

服务器处理后通常：

  • 停止媒体发送
  • 释放 RTP/RTCP 资源
  • 删除 Session
  • 释放相关状态信息

TEARDOWN 通常标志着一次 RTSP 会话的结束。

21. RTSP 状态

从实现角度，RTSP Server 通常需要维护会话状态。常见状态可以抽象为 INIT READY PLAYING 。其典型转换关系：

TEARDOWN 可以从 READY 或 PLAYING 状态结束 Session。服务器需要根据当前状态判断请求是否合法。例如，如果尚未执行 SETUP，直接发送 PLAY

INIT
  └── PLAY

服务器可能返回错误，因为媒体传输参数尚未建立。

22. RTSP 状态码

RTSP 使用三位数字状态码表示请求处理结果。其设计与 HTTP 状态码形式相似。

22.1 2xx

表示请求成功。最常见：

// 200 OK
RTSP/1.0 200 OK

22.2 3xx

通常与资源重定向有关。实际支持情况取决于具体实现。

301 Moved Permanently
302 Found

22.3 4xx

表示客户端请求存在问题。常见状态包括：

400 Bad Request
401 Unauthorized
404 Not Found
405 Method Not Allowed
454 Session Not Found
461 Unsupported Transport

其中两个状态在 RTSP 调试中尤其常见：

454 Session Not Found

服务器无法找到客户端指定的 Session。可能原因：

  • Session ID 错误
  • Session 已超时
  • Session 已被 TEARDOWN
  • Server 重启后会话状态丢失

461 Unsupported Transport

服务器不支持客户端请求的 Transport 参数。例如客户端要求某种 UDP 传输方式，而服务器仅支持 TCP interleaved。

22.4 5xx

通常表示服务器内部处理失败。例如：

500 Internal Server Error
501 Not Implemented
503 Service Unavailable

23. 重要 RTSP Header

RTSP 报文中包含多个重要 Header。其中初学阶段应重点掌握以下字段：

Header 作用
CSeq 请求序号
Session RTSP 会话标识
Transport 媒体传输参数
Content-Type 消息体类型
Content-Length 消息体长度
Accept 客户端可接受的数据格式
Public Server 支持的 RTSP 方法
Range 媒体播放时间范围
RTP-Info RTP 播放相关信息

前三个字段最关键 CSeq Session Transport 。可以分别理解为：

CSeq → 当前请求
Session → 当前会话
Transport → 当前媒体传输方式

24. Content-Type 与 Content-Length

当 RTSP 消息包含消息体时，通常需要使用：

Content-Type
Content-Length

例如：

Content-Type: application/sdp
Content-Length: 186

表示：

  • 消息体类型为 SDP
  • 消息体长度为 186 字节

随后才是具体 SDP 内容。这与常见文本协议的消息解析方式一致。

25. Range

Range 用于表示媒体播放范围。例如：

Range: npt=0-

其中 npt 表示 Normal Play Time。例如：

Range: npt=10-20

可以表示请求播放媒体时间轴中的 $10s \sim 20s$ 范围。对于实时流和文件点播，其 Range 行为可能存在区别。

26. RTP-Info

PLAY 成功后，服务器响应中可能包含 RTP-Info ，例如：

RTP-Info: url=rtsp://example.com/media/track1;
seq=45102;
rtptime=12345678

其中可能包括：

  • RTP Stream URI
  • 初始 RTP Sequence Number
  • RTP Timestamp

客户端可以利用这些信息建立 RTSP 播放时间与 RTP 数据之间的对应关系。

27. 多媒体轨道

一个媒体资源可能同时包含：

Video Track
Audio Track

例如 SDP 中：

m=video ...
a=control:trackID=0

m=audio ...
a=control:trackID=1

此时客户端通常需要分别对不同媒体轨道执行 SETUP。例如：

SETUP .../trackID=0

建立视频传输；随后：

SETUP .../trackID=1

建立音频传输。两条轨道可以属于同一个 RTSP Session。

因此需要区分 RTSP Session 与 RTP Stream ，一个 RTSP Session 可以管理多个 RTP Stream。

28. Aggregate Control 与 Media Control

RTSP 控制对象可能具有不同粒度。例如：

rtsp://example.com/movie

可能代表整个媒体资源。而：

rtsp://example.com/movie/track1

可能代表其中一个视频轨道。因此某些请求针对 Aggregate URI 整个媒体会话；某些请求针对 Media URI 单独媒体轨道。具体控制方式通常由 SDP 中等字段共同决定。

29. Session Timeout

RTSP Server 通常不会无限期保存一个没有活动的 Session。服务器可能在 Session 响应中返回超时参数，例如：

Session: 12345678;timeout=60

表示 $Session Timeout = 60 s$ ；如果客户端长时间没有发送任何会话相关请求，服务器可能释放 Session。因此部分客户端会周期性发送：

GET_PARAMETER

或者其他允许的请求进行会话保活。

30. GET_PARAMETER

GET_PARAMETER 可以用于：

  • 查询服务器参数
  • 查询媒体参数
  • 作为 Session Keepalive 使用

例如：

GET_PARAMETER rtsp://example.com/media RTSP/1.0
CSeq: 8
Session: 12345678

部分 RTSP 实现通过周期性发送该请求维持 Session 活跃状态。但具体保活方式取决于服务器实现。

即 RTP 数据与 RTSP 控制消息共享同一 TCP 连接。该机制属于 RTSP Transport 的重要内容，将在后续传输模式章节展开。

33. 完整 RTSP 会话示例

下面给出一个简化的单视频流 RTSP 会话。

33.1 OPTIONS

客户端：

OPTIONS rtsp://example.com/media RTSP/1.0
CSeq: 1

服务器：

RTSP/1.0 200 OK
CSeq: 1
Public: OPTIONS, DESCRIBE, SETUP, PLAY, PAUSE, TEARDOWN

33.2 DESCRIBE

客户端：

DESCRIBE rtsp://example.com/media RTSP/1.0
CSeq: 2
Accept: application/sdp

服务器：

RTSP/1.0 200 OK
CSeq: 2
Content-Type: application/sdp
Content-Length: ...

v=0
...
m=video 0 RTP/AVP 96
a=rtpmap:96 H264/90000
a=control:track1

33.3 SETUP

客户端：

SETUP rtsp://example.com/media/track1 RTSP/1.0
CSeq: 3
Transport: RTP/AVP;unicast;client_port=5000-5001

服务器：

RTSP/1.0 200 OK
CSeq: 3
Session: 12345678
Transport: RTP/AVP;unicast;
client_port=5000-5001;
server_port=6000-6001

33.4 PLAY

客户端：

PLAY rtsp://example.com/media RTSP/1.0
CSeq: 4
Session: 12345678

服务器：

RTSP/1.0 200 OK
CSeq: 4
Session: 12345678

随后：

Server UDP 6000
      │ RTP
      ▼
Client UDP 5000

33.5 TEARDOWN

客户端：

TEARDOWN rtsp://example.com/media RTSP/1.0
CSeq: 5
Session: 12345678

服务器：

RTSP/1.0 200 OK
CSeq: 5
Session: 12345678

会话结束。

34. 典型会话中的关键信息变化

可以将整个流程归纳如下：

阶段 主要目标 关键字段
OPTIONS 查询能力 Public
DESCRIBE 获取媒体描述 Content-Type、SDP
SETUP 建立媒体传输 Transport、Session
PLAY 启动媒体发送 Session、Range
PAUSE 暂停媒体 Session
TEARDOWN 结束会话 Session

逻辑关系为：

DESCRIBE → 明确媒体内容
SETUP → 明确媒体如何传输
PLAY → 启动媒体传输
TEARDOWN → 释放媒体会话

35. RTSP 与 HTTP 的主要差异

RTSP 和 HTTP 在报文格式上较为相似，但协议目标不同。

对比项 HTTP RTSP
主要用途 Web 资源传输 实时媒体会话控制
交互模型 请求/响应 请求/响应 + 会话状态
Session 通常不依赖协议级会话状态 核心机制
播放控制 非主要职责 PLAY、PAUSE 等
媒体传输 通常由 HTTP 本身承载 常由 RTP 等协议承载
Transport 协商 通常不涉及 RTSP 核心机制之一

因此 RTSP 可以理解为一种：

面向实时媒体资源的有状态控制协议。

36. 常见理解误区

36.1 RTSP 连接建立后即开始发送视频

不成立。通常需要先执行：

DESCRIBE
SETUP
PLAY

服务器才会开始发送媒体数据。

36.2 SETUP 等同于开始播放

不成立。SETUP 主要用于建立：

Transport
Session
RTP/RTCP 参数

PLAY 才负责启动媒体发送。

36.3 Session 等同于 TCP 连接

不成立。TCP Connection 属于传输层；RTSP Session 属于应用层。

36.4 一个 RTSP Session 只能对应一个 RTP Stream

不成立。同一个媒体资源可能包括：

Video
Audio
Subtitle

多个媒体轨道。一个 RTSP Session 可以管理多个媒体 Stream。

36.5 RTSP 负责视频编码

不成立。RTSP 并不负责 H.264、H.265 等视频编码。编码属于媒体编码层：

Raw Video
    ↓
H.264 / H.265

RTSP 只负责相关媒体会话控制。

37. 本文知识结构总结

本篇需要重点掌握以下关系：

RTSP Client
      │ Request
      ▼
RTSP Server
  • 请求通过 CSeq 进行顺序匹配
  • 服务器通过 Session 维护媒体会话
  • 双方通过 Transport 协商媒体数据传输方式

完整流程可概括为：

OPTIONS → 查询服务器能力
DESCRIBE → 获取 SDP
SETUP → 协商 Transport → 创建 Session
PLAY → 开始媒体传输
PAUSE → 暂停媒体传输
TEARDOWN → 释放 Session

其中最重要的三个 RTSP Header 为：

CSeq
Session
Transport

理解这三个字段后，RTSP 报文结构和会话逻辑基本能够建立完整框架。

  • RFC 7826 — Real-Time Streaming Protocol Version 2.0
  • RFC 3550 — RTP: A Transport Protocol for Real-Time Applications
  • RFC 4566 — SDP: Session Description Protocol
