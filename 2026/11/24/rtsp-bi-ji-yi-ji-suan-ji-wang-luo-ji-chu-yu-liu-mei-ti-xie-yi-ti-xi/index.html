RTSP 笔记（一）：计算机网络基础与流媒体协议体系

1. 引言

RTSP（Real Time Streaming Protocol，实时流传输协议） 属于计算机网络应用层协议，主要用于建立和控制实时媒体会话。

在进一步学习 RTSP 请求方法、会话管理、RTP 数据传输及 SDP 媒体描述之前，需要首先建立完整的网络通信基础，包括：

  1. TCP/IP 分层模型
  2. IP 地址与网络寻址
  3. 端口与进程通信
  4. Socket 编程接口
  5. TCP 与 UDP 传输机制
  6. 客户端/服务器通信模型
  7. 应用层协议
  8. 实时媒体传输协议体系

这些概念共同构成 RTSP 协议运行的基础环境。

本文从网络通信的基本过程出发，逐步建立 RTSP 所处的协议体系，为后续分析 RTSP 会话和媒体传输过程提供基础。

2. 网络通信基本模型

计算机网络的主要目标之一，是实现不同主机之间的数据交换。对于应用程序而言，网络通信可以抽象为：

应用程序 A 产生的数据需要经过操作系统网络协议栈处理，通过物理网络发送至目标主机，再由目标主机的协议栈将数据交付给应用程序 B。

实际通信过程并非简单的数据直接传递，而需要解决多个不同层次的问题，例如：

  • 目标主机定位
  • 数据传输路径选择
  • 目标应用程序定位
  • 数据可靠性控制
  • 数据顺序控制
  • 应用数据格式定义
  • 通信状态管理

为了降低网络系统复杂度，这些功能按照不同职责划分为多个协议层。

3. TCP/IP 网络体系结构

3.1 分层设计

现代互联网主要建立在 TCP/IP 协议体系之上。学习应用层网络协议时，可以使用以下四层模型进行理解：

不同协议层负责不同类型的问题。

层次 主要职责 典型协议
应用层 定义应用程序之间的数据交换规则 HTTP、RTSP、DNS、FTP
传输层 实现进程之间的数据传输 TCP、UDP
网络层 实现不同主机之间的数据传递 IPv4、IPv6
网络接口层 实现局域网络中的数据帧传输 Ethernet、Wi-Fi

RTSP 位于应用层，其运行依赖下层提供的网络通信能力。

5. IP 地址与网络层通信

5.1 IP 地址的作用

IP 协议负责实现主机之间的数据传输。IP 地址用于标识 IP 网络中的通信节点。

常见 IPv4 地址形式为：

192.168.1.10
192.168.1.20
10.0.0.5

IPv4 地址长度为 32 bit，通常采用点分十进制形式表示。例如：

192.168.1.10

其本质为：

11000000.10101000.00000001.00001010

9. TCP 传输协议

9.1 TCP 基本特征

TCP（Transmission Control Protocol）是一种：

  • 面向连接；
  • 可靠；
  • 面向字节流；
  • 全双工；

的传输层协议。其主要目标是为应用程序提供可靠的数据传输能力。

9.2 TCP 连接

TCP 通信通常需要首先建立连接。典型建立过程称为 三次握手：

连接建立后，双方可以进行双向数据传输。

9.3 TCP 可靠性机制

IP 网络本身并不保证数据一定成功到达。TCP 在此基础上增加了多种可靠性机制，包括：

  • 序列号；
  • 确认应答；
  • 超时重传；
  • 流量控制；
  • 拥塞控制；
  • 数据顺序恢复。

假设发送方依次发送：

Packet 1
Packet 2
Packet 3

若 Packet 2 在网络中丢失：

Sender                       Receiver

Packet 1 -------------------> ✓
Packet 2 --------X
Packet 3 -------------------> ✓

        Packet 2 retransmit

Packet 2 -------------------> ✓

TCP 可以检测数据丢失并进行重新传输。

9.4 TCP 字节流特性

TCP 提供的是 Byte Stream（字节流），而不是应用消息边界。例如发送端执行：

send("ABC");
send("DEF");

接收端可能读取为 “ABCDEF”；也可能分为：

"AB"
"CDEF"

TCP 只保证字节顺序和可靠交付，并不保留应用程序每次 send() 的边界。因此应用层协议通常需要定义自己的消息边界，例如：

  • 固定长度；
  • 长度字段；
  • 特殊分隔符；
  • 完整协议头。

10. UDP 传输协议

10.1 UDP 基本特征

UDP（User Datagram Protocol）是一种：

  • 无连接；
  • 面向数据报；
  • 协议结构简单；
  • 不提供可靠传输保证；

的传输层协议。

UDP 数据传输通常不需要建立类似 TCP 的连接。其基本过程可以表示为：

Sender                          Receiver

 Datagram 1 -------------------->
 Datagram 2 -------------------->
 Datagram 3 -------------------->

10.2 UDP 数据报

UDP 保留消息边界。发送：

Datagram A
Datagram B

接收端仍以独立数据报的形式接收。与 TCP 字节流不同：

TCP
--------------------------------
A B C D E F G H ...
连续字节流

UDP
--------------------------------
[ Datagram A ]
[ Datagram B ]
[ Datagram C ]
独立数据报

10.3 UDP 不提供的机制

UDP 本身不保证：

  • 数据一定到达；
  • 数据只到达一次；
  • 数据按照发送顺序到达；
  • 丢失数据自动重传。

例如：

Sender                       Receiver

Packet 1 -------------------> Packet 1
Packet 2 --------X
Packet 3 -------------------> Packet 3

UDP 不会因为 Packet 2 丢失而自动重新发送。如应用需要可靠性，需要由应用层或其他协议自行实现。

11. TCP 与 UDP 对比

特性 TCP UDP
连接方式 面向连接 无连接
数据形式 字节流 数据报
可靠性 提供可靠传输 不保证可靠传输
顺序保证 保证 不保证
自动重传 支持 不支持
流量控制 支持 不支持
拥塞控制 支持 不支持
协议开销 相对较高 较低
实时性 受重传等机制影响 通常更易实现低延迟
消息边界 不保留 保留

TCP 和 UDP 不存在绝对优劣，其选择主要取决于应用需求。例如：

可靠性优先 → TCP 更常见
低延迟、允许一定数据丢失UDP → 更常见

12. 应用层协议

12.1 应用层协议的作用

TCP 和 UDP 负责数据传输，但并不规定数据内容的业务含义。例如 TCP 只能保证下面的字节可靠传输：

47 45 54 20 2F 20 48 54 54 50 ...

这些字节具体表示什么，需要由应用层协议进行定义。

应用层协议通常规定：

  • 消息格式；
  • 请求类型；
  • 响应格式；
  • 状态码；
  • 字段含义；
  • 会话流程；
  • 错误处理规则。

常见协议包括：

HTTP
DNS
FTP
SMTP
SSH
RTSP

13. HTTP 与 RTSP 的协议层级关系

HTTP 和 RTSP 都属于应用层协议。可以表示为：

二者均采用文本化请求/响应形式的协议设计思想，因此 RTSP 消息格式在外观上与 HTTP 存在一定相似性。

例如 HTTP 请求：

GET /index.html HTTP/1.1

RTSP 请求可能表现为：

需要注意：

RTSP 与 HTTP 是两个独立协议，不能因消息格式相似而将 RTSP 视为 HTTP 的扩展。

RTSP 更强调实时媒体会话控制。

15. 实时媒体传输的主要问题

实时媒体与普通文件传输存在明显差异。典型实时媒体数据具有以下特点：

  • 数据连续产生；
  • 数据量较大；
  • 对时间关系敏感；
  • 通常允许有限的数据丢失；
  • 对传输延迟较敏感；
  • 音视频之间可能需要同步。

因此媒体传输除基本网络通信外，还需要解决：

帧顺序
   │
   ├── 数据包顺序判断
   │
播放时间
   │
   ├── 时间戳
   │
网络抖动
   │
   ├── Jitter Buffer
   │
数据丢失
   │
   ├── 丢包检测
   │
音视频同步
   │
   └── 时钟同步

仅使用 TCP 或 UDP 并不能完整描述这些媒体层语义，因此产生了 RTP、RTCP 等专门面向实时媒体的协议。

16. RTSP、RTP、RTCP 与 SDP

学习 RTSP 时，需要同时区分以下四类协议或描述规范：RTSP ; RTP ; RTCP ; SDP 。它们承担不同职责。

16.1 RTSP

RTSP：Real Time Streaming Protocol 主要用于**实时媒体会话的建立和控制。**典型控制行为包括：

查询服务器能力
获取媒体描述
建立媒体传输参数
开始播放
暂停播放
结束会话

可以将其定位为：

RTSP：Session Control（会话控制）

RTSP 通常并不直接承担大规模音视频媒体数据本身的传输。

17. RTP

RTP：Real-time Transport Protocol 主要用于**实时音视频数据的传输。**RTP 在媒体数据基础上增加：

  • Sequence Number；
  • Timestamp；
  • Payload Type；
  • SSRC；

等信息。一个简化 RTP 数据包结构可表示为：

其中：

Sequence Number主要用于判断 RTP 数据包顺序和检测丢包。

Timestamp主要用于描述媒体数据的时间关系。

Payload Type用于标识 RTP Payload 的数据类型或对应的编码格式映射。

SSRC用于标识 RTP 同步源。

18. RTCP

RTCP：Real-time Transport Control Protocol 通常与 RTP 配合使用。RTP 负责媒体数据：

Media Sender
      │
      │ RTP
      ▼
Media Receiver

RTCP 则负责传输一定的控制和统计信息：

Media Sender
      ▲
      │ RTCP
      │
Media Receiver

RTCP 可用于提供：

  • RTP 数据包接收统计；
  • 丢包情况；
  • 抖动信息；
  • 发送端与接收端统计；
  • 媒体同步相关信息。

因此：

RTP → 负责媒体数据
RTCP → 负责媒体传输状态反馈及相关控制信息

19. SDP

SDP：Session Description Protocol 名称中虽然包含 Protocol，但其核心作用更接近一种：会话描述格式。

SDP 可以描述：

  • 媒体类型；
  • 编码方式；
  • 网络地址；
  • 端口；
  • Payload Type；
  • 时钟频率；
  • 音视频轨道信息。

典型 SDP 内容可能包含：

v=0
o=- 123456 1 IN IP4 192.168.1.20
s=Example Stream
t=0 0
m=video 5004 RTP/AVP 96
a=rtpmap:96 H264/90000

其中：m=video 表示媒体类型为视频。5004 表示对应媒体传输端口。RTP/AVP 表示使用 RTP Audio/Video Profile。96 为动态 Payload Type。H264/90000 描述该 Payload Type 对应 H.264，以及 RTP 时钟频率信息。

SDP 本身通常不负责媒体数据传输。

实时媒体系统还经常涉及：

Unicast
Multicast

28.1 单播

单播表示一个发送方与一个接收方之间建立数据传输关系。

Server ─────> Client A
Server ─────> Client B
Server ─────> Client C

服务器通常需要分别向不同客户端发送数据。

28.2 组播

组播允许发送方将数据发送到一个组播地址，由多个加入该组的接收端接收。

                ┌──> Client A
Server ────────—┼──> Client B
                └──> Client C

组播适合某些一对多分发场景，但要求网络基础设施支持 IP Multicast。

RTSP 可以与不同媒体传输模式配合使用，其具体协商机制将在后续 Transport 相关章节展开。

29. 网络延迟、抖动与丢包

实时媒体系统中存在三个重要网络指标。

29.1 延迟 Latency

延迟表示数据从发送端到接收端经历的时间。可以表示为：

Sender
   │
   │------------------------>
   │       50 ms
Receiver

端到端媒体延迟通常不仅包含网络传输时间，还可能包含：

采集延迟+编码延迟+网络延迟+缓冲延迟+解码延迟+渲染延迟

29.2 抖动 Jitter

如果连续数据包的网络传输时间不稳定：

Packet 1：20 ms
Packet 2：24 ms
Packet 3：65 ms
Packet 4：18 ms

这种到达时间变化称为抖动。媒体播放器通常使用：Jitter Buffer 对网络抖动进行一定程度的吸收。

29.3 丢包 Packet Loss

网络可能发生数据包丢失：

Packet 100
Packet 101
Packet 102   X
Packet 103
Packet 104

RTP 序列号可以帮助接收端发现数据包缺失。例如：

Sequence:
100
101
103
104

接收端可以判断：Sequence 102 Missing。具体的恢复策略由应用需求和上层机制决定。

30. RTSP 在协议体系中的定位

综合前述内容，RTSP 的位置可以表示为：

需要建立以下基本认识：

  1. RTSP 属于应用层协议；
  2. RTSP 主要负责实时媒体会话控制；
  3. RTSP 通常不承担音视频媒体数据本身的大规模传输；
  4. SDP 用于描述媒体会话；
  5. RTP 用于承载实时媒体数据；
  6. RTCP 用于媒体传输统计、反馈和同步相关信息；
  7. RTP 可以运行在 UDP 等传输机制之上；
  8. 所有相关通信最终依赖 IP 网络完成主机间传输。

32. 常见概念辨析

32.1 RTSP 与 RTP

RTSP → 会话控制
RTP → 媒体数据传输

二者用途不同。

32.2 RTP 与 UDP

RTP → 实时媒体数据组织
UDP → 通用传输层数据报服务

RTP 通常运行在 UDP 之上，但 RTP 不等于 UDP。

32.3 RTSP 与 TCP

RTSP → 应用层协议
TCP → 传输层协议

二者属于不同网络层次。

32.4 RTSP 与 H.264

RTSP → 网络会话控制协议
H.264 → 视频压缩编码标准

RTSP 可以控制 H.264 媒体流，也可以控制其他编码格式的媒体流。

32.5 RTP 与 H.264

RTP 可以承载 H.264 数据，但 H.264 数据通常需要按照相应 RTP Payload Format 规则进行分包。逻辑关系为：

H.264 NAL Unit
      │
      ▼
RTP Packetization
      │
      ▼
RTP Packet

具体 H.264 RTP 分包机制将在后续文档中展开。

32.6 SDP 与媒体数据

SDP 描述媒体属性：

视频类型
编码格式
Payload Type
时钟频率
媒体地址
媒体端口

但 SDP 本身不承担媒体数据传输。
